Ambient architecture · implementation frontier

The baseline works. The internal ownership still needs rescue.

Proven behaviour and target product concepts are deliberately wider than the current architecture frontier. The next cut is selected for leverage and proofability, not because it was pre-committed as a phase.

01 · Frontier stack

Know what is proven, leaky, and absent

“Not implemented” is not the same as “architecturally broken.” Rescue only the boundary needed for the active slice while preserving the behaviour below it.

02 · Rescue comparison

Conversation wins on leverage

Scores combine leverage, interface certainty, dependency value, deterministic proofability, and inverse risk. They are selection evidence, not a permanent roadmap.

03 · Selection rationale

One active cut, one likely next

The mapping creates ordering constraints without turning uncertain future work into phases.

Active: Conversation service and store

  • It is already a complete proven durable vertical path.
  • Mutation overlap is concrete and testable today.
  • Its ports reduce uncertainty for models, WhatsApp effects, proofs, and Root handoffs.
  • The cut requires no live model invocation or WhatsApp send.

Likely next: model runtime

Conversation currently constructs Qwen and Pi directly and contains Model<any>. Once the role boundary is clean, one structured model module can bind Qwen and local Vibe without creating a parallel application graph.
